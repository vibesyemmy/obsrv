## DECISION 2026-09-17 by Henry: the inventory buys no fences

Asked by Kenya before building (room #427): a second `OBSRV_TEST`-fenced hook in `src/`, to force
`frameCheck:21` — *"the renderer did not say which frame it drew"* — by never sending `drawNow`.
Carefully written, fenced twice, inert when unset. **Declined, and the rule is general:**

> **A sentence reachable only by changing the product is recorded as reachable, citing the control
> run that produced it, and parked. A test-only fence in `src/` has to be bought by a defect, not by
> an audit.**

**Why.** The observation already exists without the fence: `#139`'s control removed the `drawNow`
send and the sentence appeared in a real reply. That is the standard every control on this board is
held to, so the claim — *"this sentence is reachable when a draw is never acknowledged"* — is already
supported, and citing the run is the whole of what the fence would add to the record.

**What the fence would really buy is a standing regression test**, and its cost is that it sits in
the path every capture takes. A permanent risk to every capture, in exchange for pinning one
diagnostic sentence with no defect behind it, is the wrong trade.

**The precedent it would have leaned on cuts the other way.** `OBSRV_TEST_THROTTLE_REFUSAL` exists
because a real bug shipped a refusal to stderr only and needed a standing guard: **the defect bought
the fence.** c5 is an audit of what the product says in the field, and an audit that edits its
subject to make it speak has stopped measuring it.

**If `frameCheck:21` ever bites** — a stale capture nobody was warned about — that defect buys the
fence, and the sentence gets its standing test then.

## PLAN 2026-09-17 by Henry: the launch cluster (5), and why the guard stays untouched

Claimed on Wren's routing. **Written down before any code, because the first design was wrong and the
second only exists because the product was measured.**

**The five sentences** are in `ensureLive` (`src/mcp/control.ts:310-360`): the app could not be
launched; the launch exited immediately into a profile already in use; consent went unanswered; the
app was launched but did not answer; agent control is off (`lib.ts:581`).

**The first design, which is not being built.** All five sit behind `OBSRV_TEST`, whose guard says
why — *"the e2e harness must never launch a real Obsrv"* (`mcp/lib.ts:617`), with `launchApp`
refusing again at `mcp/launch.ts:91`. I proposed gating an exception past it. **Wren's rule — measure
whether the product can already do it before designing around a guard — applied to my own proposal,
and the answer is that it can.**

**The design: the dev lane, which already ships the isolated path.** `scripts/devLane.js:123`
`appLaunch(root, env)` returns the built tree's entry (`<root>/out/main/index.js`), an isolated
profile (`--user-data-dir=<devHome>/profile`, where `devHome` is **`OBSRV_DEV_HOME`** or
`~/.obsrv-dev`, `:22-29`), and a window titled "dev lane" so it is never taken for the installed app.
`mcp-live.spec` is the precedent for the other half: it runs the MCP server **without** `OBSRV_TEST`.
So the spec sets `OBSRV_DEV=1` and `OBSRV_DEV_HOME=<mkdtemp>`, every launch goes to the built tree on
a throwaway profile, and **`cannotLaunchReason` and `launchApp`'s throw stay exactly as they are for
every other caller.** No test-only code in `src/`.

**The hazard that design carries, and how the spec closes it** (Wren): `profileDir` falls back to
`~/.obsrv-dev` when `OBSRV_DEV_HOME` is unset, so a spec that forgets it — or a refactor that drops
it from the env — would silently drive **Opeyemi's own dev lane and window**, and nothing in the run
would say so. The spec reads `OBSRV_DEV_HOME` at setup, asserts it is set and under `os.tmpdir()`,
and fails with *"this spec must not run against the real dev lane"* otherwise. Loud in exactly the
case where silence costs most.

**Constraints on the work:**
- **CI only**, and **a local run needs Opeyemi's separate yes**, as the desk-taking specs do: it opens
  a real window.
- A stray window on a runner is identifiable in a screenshot by its "dev lane" title.
- **A unit test through the injected deps is not evidence** — it constructs all five and observes none.

**Reachability, as far as reading goes:**
- *the launch exited immediately, profile already in use* — clean: the harness holds the lane profile
  and the server's instance loses the lock;
- *nobody answered the consent prompt* — a lane app with control off, and the 12 s `LAUNCH_TIMEOUT_MS`;
- *the app could not be launched* — to check: a lane with no built entry fails in `resolveDevTarget`,
  which may produce a different sentence;
- *launched but did not answer* — likely **parked with a reason** rather than built, since reaching it
  wants a fake app that comes up and stays silent, and a fake asserts our belief about a state instead
  of observing it.
