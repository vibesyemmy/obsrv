# 0.57.0, with dev-time targets as a standing part of the run

The fourteenth run, and the first where the dev server is not an
experiment but half the plan — run 13 found two of its three findings
there, so it stops being optional. Against youtube.com (the largest
custom-elements site there is), zalando.de (a European retailer, where a
consent wall was hoped for), codepen.io (embeds and dark chrome), and a
dev server on localhost carrying four shapes a designer meets: an
ordinary page, a route the server does not have, a page reloading under
the measurement, and a route that bounces to a login.

## Held

- **A fix from this morning fired in the wild, unprompted.**
  youtube.com redirects itself to `?themeRefresh=1` after load, and the
  answer said so: "the page navigated after it loaded, to
  https://www.youtube.com/?themeRefresh=1 … the figures are of the page
  it arrived at". 0.57.0 shipped that sentence six hours earlier, pinned
  only on a fixture. This is it meeting a real page.
- **Both dev-time fixes hold on a real dev server.** The missing route:
  "the server answered 404 Not Found … the figures are of the error page
  it sent, not of the page asked for — check the route, the port, and
  that the server has it". The reload: named with the `?n=2` it arrived
  at, 11 targets, which is revision 2 by the fixture's construction.
- **The rules keep finding things.** zalando.de: 143 targets, **103 under
  7 mm** — sixty 20 px carousel buttons, forty 21 px nav links.
  codepen.io: two contrast findings on its own sponsor block (2.33:1 and
  4.4:1 against a dark ground) and six oversized images.
- **A silence that was correct.** youtube.com drew no shadow-root note,
  and that is right: modern YouTube renders its custom elements into the
  light DOM, measured directly — 95 interactive elements in the light
  DOM, **zero open shadow hosts**. The note fires on the condition, not
  on the framework.

## Broke or misled, ranked

1. **A redirect during the initial load is invisible, and it is the
   "page behind a login" case.** Asked for `/private`; the dev server
   answered `302 → /login`; the audit measured the login page — 2
   targets, an email field and a Continue button — and said nothing at
   all. No note, no status, nothing to say the page measured is not the
   page asked for.

   It sits exactly between the two fixes 0.57.0 shipped. A navigation
   *after* load is named (youtube.com, above). An error *status* is named
   (the 404 route, above). A redirect *during* load that ends in a 200 is
   named by neither: there is no post-load navigation to report, and the
   final status is a perfectly good 200.

   The cost is worst in the case it belongs to. A designer points Obsrv
   at their authenticated route, the dev server bounces them to the login
   page, and they are handed two targets where they expected fifty, with
   no explanation — the natural reading is that their page is broken.
   Every ingredient is already in the tree: `did-navigate` fires for the
   redirect, and `httpStatus()` already keeps what it carries.

## Still not seen in the wild

**The dialog note has now failed to appear across nine live sites** over
three runs, including the consent-wall publishers and retailers it was
written for. It remains fixture-proven only. Either the region-gating on
this machine never draws such a wall, or the shape is rarer in the wild
than the fixture suggests; neither is settled by more attempts of the
same kind, so the next attempt should be from a network that draws
consent walls, or against a product's own staging where the modal can be
opened deliberately.

## A hypothesis that did not survive

This run began with the idea that youtube.com would show the shadow-root
counts working at scale, since Polymer is a shadow-DOM framework. It has
none. The counts stayed at zero and the note stayed silent, correctly.
Recorded because the check took a minute and the assumption would have
become a claim.
