# 0.45.0 driven against five more live sites

The fourth run of the day, on a stack that is 0.45.0 end to end, against
youtube.com (a different page under a mobile UA, animation, an endless
feed), airbnb.com (lazy srcset cards under a sticky header), theguardian.com
(a consent layer, thousands of links, hairlines), docs.python.org (a static
baseline) and linear.app (dark backgrounds and thin type on the 11.6"
Chromebook preset with the budget panel). Headless, live, and every surface.
The site is the fixture; this reports on the tool.

## Held

- **The 0.45.0 additions, on real pages.** The frame-identity check stayed
  silent on a live pane capture and a live window capture of youtube.com's
  mobile page, which is what it should do in the ordinary case. A cut load
  under budget-phone on airbnb.com captured the page's skeleton state as
  `loading`, honestly. The drive settled after the new tab's preset.
- **Walks to the end** on linear.app (8 screenfuls), airbnb.com (5 bands
  with the sticky header hidden), the Guardian audit (14 screenfuls, 20,596
  px, 236 targets) when the page let it.
- **inspect** on linear.app's h1 at 135 ppi on Budget TN: 64 px = 12.03 mm,
  18.73:1 as stated and 9.65:1 on the panel. **diff** on the Python docs:
  settled, ink −0.39 %, one band finding. **text scale** 1.5 on the same page:
  four targets, since the index's links are inline and exempt by rule.

## Broke or misled, ranked

1. **A scroll-locked page passes for a one-screen page.** theguardian.com
   opens under a full-screen cookie consent layer that locks the body's
   scroll. The walk, headless and live alike, answered `walked: { screenfuls:
   0, atEnd: true }`, and the audit in the same call measured 239 targets on
   a 20,596 px page behind the layer — findings a finger cannot reach, and no
   word about the layer. The band capture, which scrolls the root directly,
   went through. Two things to do: `walkStep` should tell a page that will
   not move from a page with nowhere to go (a document taller than its
   viewport whose scroller has no range is locked), and every measurement
   should check the walk's coverage against the `pageHeight` it measured and
   warn when the walk saw the end of a page it never crossed.
2. **A live `openTab` or `navigate` on a page that never stops loading is a
   40 s error.** theguardian.com in a new tab: "obsrv control openTab timed
   out after 40000 ms … re-open the app and re-enable the toolbar toggle",
   while the tab had opened and the page was there a moment later,
   `loading: false`. The error blames the app and offers headless; the CLI
   answers the same situation since 0.44.0 with the page as it stands,
   `loading`, and a warning. The live path should answer with the status,
   `loading: true`, and the same kind of warning.

Not reproduced, recorded: the first youtube.com audit through the MCP
answered `walked: 12, atEnd: false` with, as far as I recall, no note, which
the uncapped walk should not produce; every later run of that URL, headless
and local, got YouTube's consent page (2 screenfuls, 14 targets, 1,364 px),
so the page that produced the odd answer could not be measured again.

Observation, not a bug: the first Guardian report measured an interstitial
of 14 targets; the site serves different documents to different loads.

## Fixed on `fix/locked-and-loading`

- **Coverage** (ca831c0). Every measurement compares the walk's coverage with
  the page height it measured — the CLI's audit, lint and report, the live
  MCP audit and lint — and warns when the walk saw the end of a page far
  taller than what it crossed. On the Guardian, live and through the CLI
  report: "the walk saw the end after 0 screenfuls (768 CSS px), but the
  page measures 20304 CSS px (27 screenfuls): a modal or a locked scroll
  held the page, or it grew after the walk; the measurement is of the page
  as it stands, and nothing below 768 px was scrolled into view". A fixture
  that fixes its body under a layer proves the CLI path.
- **Navigate budget** (f579526). The app bounds its own wait for a navigate
  or a new tab's URL (30 s, under the MCP's 40 s guard) and answers with the
  URL and `loading: true` when the load is still going; the MCP turns that
  into a warning on snap, drive, audit, lint and inspect. A page whose script
  never arrives proves it in seconds; the Guardian itself loaded in 4.6 s on
  the branch build's run.
