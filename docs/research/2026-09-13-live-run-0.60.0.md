# Run 16: the first run driven by the readiness criteria

The sixteenth run, on 0.60.0's code (main `08c9648`, lane-stamped in every
answer). The change from runs 13-15 is not the sites. It is that
`docs/readiness.md` had been written four hours earlier, so the run had
questions to ask rather than only pages to drive:

- **B1** — does a run over fresh archetypes turn up anything user-visible?
- **B5** — does the same page measured twice answer the same?
- **C4** — do the two surfaces answer alike, field by field?
- **C5** — which notes have actually been seen to fire, on what, and when?

Three of those four had never been asked. Two of them found defects.

## What held

**The redirect note met a real login wall.** `github.com/settings/profile`
answers a 302 to `github.com/login?return_to=…`, and the audit said so:
*"the load of …/settings/profile ended at …/login: a login wall, a route that
has moved, or a redirect the server chose — the figures are of the page it
landed on, not of the one asked for."* Shipped in 0.59.0 against a fixture
server; this is the first time it has been right about a site. **C5: seen
firing, 2026-09-13, github.com.**

**The grew-under-the-walk note met a real feed.** `theguardian.com/international`:
the walk reached the end after 5 screenfuls (6,480 px) of a page that measures
20,523 px, and the answer named the cause rather than offering three — *"the
page grew as it was walked — a feed that extends as you scroll."* **C5: seen
firing, 2026-09-13, theguardian.com.**

**Findings a designer could act on, on four sites.**

| Site | Targets | Under 7 mm | The exemplar |
| --- | --- | --- | --- |
| github.com/login | 9 | 4 | "Manage cookies" 18 px → **4.98 mm** |
| theguardian.com | 204 | 27 | 24 × "N comments" 10 px → **2.77 mm** |
| react.dev/learn | 94 | 24 | 20 × "Download" 24 px → **6.64 mm** |
| getbootstrap.com checkout | 22 | 5 | 5 × `input.form-check-input` 16 px → **4.43 mm** |

Bootstrap's is the most actionable in the set and the least about one site:
those five are `.form-check-input` at its default size, on Bootstrap's own
checkout example, so the finding belongs to every checkout built on it.
react.dev's twenty at 6.64 mm are the opposite — just under the line, and two
readers both hesitated over whether they would act. That hesitation is **B4**
arriving before B4 has been run, and is the argument for its disagreement
rate.

## B5: the same page twice

Headless, `file://` fixtures, five runs each of `audit.html`, `lint.html`,
`many-targets.html`: **every field identical every time** — counts, groups,
`walked`, warnings. The headless surface is deterministic on identical bytes,
which nobody had checked before today.

Live, an http fixture with no redirect, three runs: identical.

Live, an http fixture **with** a redirect, three runs: **2 warnings, then 1,
then 1.** Same bytes, same surface, same build. Not noise — a defect, below.

So B5's first answer is a boundary rather than a number: deterministic
headless, deterministic live, **not deterministic live on a cold app.**

## C4: the two surfaces, field by field

Driven against locally served fixtures rather than live URLs, on obsrv-9b's
insistence and for a reason worth recording: a live URL loads twice for such a
comparison, and a site that differs between the loads makes every difference
undecidable — *the surfaces disagree* and *the page changed* look the same.
That mistake is in the 0.54.0 report as a retraction.

- `/ok`: identical field for field. Live carries `tabId`/`tabIndex`, headless
  `why`; everything else matches including `walked`.
- `/private` (302 → login): **live 2 warnings, headless 1.**
- `/gone` (302 → 404): **live 4, headless 3.**

The extra one, both times: *"the page navigated after it loaded"* — which the
page had not done.

## The defect, its two causes, and what was fixed

**Cause one: Obsrv's own window restore.** A density change recreates the
offscreen window and then re-loads the page at its own address. That commit is
real, and the arrivals record counted it as the page moving. Fixed and merged
(`e6ba0ba`): the restore keeps its status and its intended URL and withholds
only `url-changed`, cleared in a `finally` so a failed restore cannot swallow
every later navigation. Headless was never exposed — the CLI sets the viewport
before it loads, so there is no page to restore, which was checked rather than
assumed.

**The fix was real, tested red-first, and did not fix the reported symptom.**
Both halves are true and they look like one claim when a fix and a symptom are
discussed in the same breath. After merging, the live column still read 2-1-1.

**Cause two: the pane mirror.** Instrumented rather than reasoned — the third
hypothesis of the day, after two wrong ones. Logging *origin* rather than
timing, which is what separates a mirror from a restore, since both commit at
the same address a moment later:

```
expect wanted=…/private
mirror? from=native url=…/login  echo=false      ← native's post-redirect commit, not an echo
target did-navigate url=…/login                   ← the target's own load commits     (arrival 5)
mirror? from=target url=…/login  echo=true
navigateBoth resolved applied=…/private arrivals={count:5, url:…/login}   ← atCount = 5
target did-navigate url=…/login                   ← second target commit, after the resolve (6)
mirror? from=target url=…/login  echo=false
```

`seen.count` 6 > `atCount` 5, so the note fires. The origin line is the
evidence: the second commit follows `mirror? from=native`, so the bus mirrored
the visible pane's landing into the measuring pane, which loaded it again.
`expect(wanted)` is registered for `/private` and the pane commits `/login`, so
**the redirect defeats the expectation** and the commit reads as news.

The contrast case, same call with the tab already on the landing page:
`mirror? from=target … echo=true`, one commit, `atCount` equal to the final
count, no note. Which is why it is cold-only.

**Not fixed.** The direction: a commit a mirror caused is Obsrv keeping its
panes in step, not the page's news — the same sentence as the restore, one
layer out. `expect` should be left alone; it is handed an address before the
server has chosen one, and asking it to anticipate a redirect moves the defect
rather than closing it. Before building it, print the shape that would break
if mirrored commits stopped counting: a genuine same-address reload, which
should survive because the page's own script runs in both panes and the target
commits on its own account, with no `mirror? from=native` before it.

## Also found

The live **lint** measure site still compared addresses where the audit's
counts commits, so live lint could not see a reload to the same address while
live audit could. One record, two readers, one converted — the shape the
record exists to remove, surviving in the site next door. Fixed in `e6ba0ba`
with the test the audit case already had, whose absence is why only one of
them was noticed.

## What this says about readiness

- **B1: not met.** The run found user-visible defects, as runs 13-15 did.
- **B5: has its first numbers**, and found a real defect with them on the
  first outing. The fixture-first ordering is what made "2, then 1, then 1"
  legible; on live sites it would have been indistinguishable from a site
  rotating something.
- **C4: has its first pass**, on fixtures, and it is where the divergence was
  caught. A field-level pass across all tools is still unrun.
- **C5: two notes seen firing in the wild**, recorded above with dates. The
  inventory does not exist yet; these are its first two rows, and a note that
  did not fire during this run is *not* recorded as anything.
