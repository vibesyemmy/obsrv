# 0.46.0 driven against five more live sites

The fifth run, on a stack that is 0.46.0 end to end — app, plugin and the
session's MCP server, the last of which had to be reconnected before the
0.46.0 code was actually in the server process (a running server keeps the
code it started with while every headless call spawns the CLI from the npx
cache as it stands, so the pair can disagree for hours; the check is the
server process's start time against the publish time, not the version in the
cache's `package.json`).

The sites: gov.uk (a plain, well-built public page, as the control),
craigslist.org (which answered with its bot-block page, itself useful),
ikea.com (a retail grid with lazy `srcset` cards), figma.com (dark sections
and heavy art direction) and espn.com (a scoreboard that never stops
painting). Headless, live, and every surface. The site is the fixture; this
reports on the tool.

## Held

- **The 0.46.0 additions.** The walk-coverage note is silent on every page
  that actually walked: gov.uk (6 screenfuls, 4,923 px, live and headless
  agreeing), ikea (14 screenfuls, 11,894 px), figma (11 screenfuls, 8,842
  px). The navigate budget never fired, because nothing in this set hung.
- **The live review loop.** Six `scroll { page: "next" }` steps down gov.uk,
  every capture settled, `atEnd` true at 4,155 px, and a live audit
  afterwards that agreed with the headless lint on the page height to the
  pixel.
- **The rules, on real pages.** gov.uk on Budget TN: 34 `govuk-link`s at
  5.69:1 as stated and 4.49:1 on the panel, one search button at 3.91:1 as
  stated, one image downsampled 3×. ikea: `#929292` on `#cccccc` at 1.94:1,
  seven cards upscaled 1.12×, nine icons downsampled 2.5×. figma: white on
  black at 7.37:1 falling to 4.1:1 on the panel, and a 20×20 image drawn over
  310×310 (15.5×).
- **The honest refusals.** `diff` on a phone preset explained itself and
  named two 1x presets. A `fullPage` ikea capture said the PNG was 6.8 MiB
  and gave the path rather than inlining it. `inspect` said it had waited
  5.7 s for a render slot. cnn.com came back `loading` with a warning rather
  than a lie. The frame-identity diagnostic from 0.45.0 fired once, on an
  animating espn pane, and was correct: one frame behind.
- **`report`** wrote both screens with walk, audit, lint, the 1x-vs-2x diff
  on the laptop and the "dense screen has no comparison" note on the phone.

## Broke or misled, ranked

1. **A blank capture is vouched for as settled.** `obsrv snap
   https://www.espn.com --preset 1080p-24` returns a PNG that is one opaque
   white end to end — `settled: true`, no `unsettledReason`, no warnings —
   five times out of five on the CLI, again through the MCP, and again in
   the live app pane the user is watching. The page is there: an audit of
   the same URL in the same run measured 110 targets and 299 text elements on
   a 5,641 px page, so the DOM path and the raster path answered about
   different things without either saying so. A `--wait` sweep locates it:
   0 ms and 500 ms give a blank frame called settled, 1000 ms gives 93.7 % of
   the frame painted, 1500 ms and beyond give 98 % and an honest
   `animating`. The mechanism is not the redirect — `africa.espn.com`, the
   page espn.com redirects to, renders correctly 2/2, and a local fixture
   reproduces without any redirect: a page that paints an opaque
   full-viewport layer at once and paints its content 2.5 s later comes back
   blank and settled 3/3. Quiescence is measured in paints, so a page that
   goes genuinely quiet while showing nothing is indistinguishable from one
   that has finished. `captureQuiescent` already rescues a frame that was
   never fully painted (`uncovered`, with a warning naming the region);
   there is no equivalent for a frame that was painted and is empty. A
   one-colour frame is never a real answer, and the tool's whole promise is
   the picture.

2. **Millimetres are inflated on any page without a viewport meta tag, in the
   direction that hides problems.** On berkshirehathaway.com at `android-65`
   the audit reports the smallest text as 10 px = 1.88 mm and the GEICO link
   as 75×15 px = 2.82 mm. Chromium lays a page with no viewport meta out at
   980 CSS px and scales it into the 360 px visual viewport, so those are
   really 3.67 CSS px = 0.69 mm and 27.6×5.5 CSS px = 1.04 mm — the figures
   are 2.72× too large, and text that is far under the 2 mm threshold is
   reported as clearing it. `inspect` repeats the same inflation (a 44 px
   button on the fixture: 8.28 mm reported, 3.04 mm drawn), and `lint`
   inverts an image verdict with it: it calls the GEICO logo "75×15 px drawn
   over 150×30 device px: upscaled 2×" when the image is in fact drawn at
   55 device px and downsampled. Same root cause, third symptom: the
   walk-coverage note added in 0.46.0 fires falsely on these pages, because
   it compares a page height in layout px (2,178, which is exactly one
   screenful: 800 × 980/360) against the preset's 800 CSS px and concludes
   the walk missed two screenfuls of a one-screen page. Seen on
   berkshirehathaway.com and on craigslist.org's block page; a fixture pair
   (the same markup with and without the meta tag) isolates it.

3. **`obsrv_audit` has no `groupsOnly`.** An audit of ikea's UK home page at
   `iphone-61` came back as roughly fifteen thousand tokens: 223 targets and
   291 text elements, 146 and 93 of them under the thresholds, 39 findings
   dropped by the truncation cap, and eleven groups carrying the whole story
   at the end. `obsrv_lint` has taken `groupsOnly` since 0.32.0 and the
   skill tells the caller to quote a group rather than its members, but the
   audit gives no way to ask for only the groups. On a real retail page at a
   phone preset the flag is the difference between an answer that fits and
   one that crowds out the rest of the review.

## Fixed on `fix/blank-and-layout-scale`

1. **A quiet one-colour frame is not a settled capture.** Both capture paths
   — `captureQuiescent` for the headless CLI and the app's raster, and the
   live `quiesce` behind every pane and window capture — now test the frame
   they are about to vouch for. One colour end to end after the quiet
   window, it is held for a three-second grace (`BLANK_GRACE_MS`, cited by
   both like the quiet window itself); a page that paints inside the grace
   is captured with the page on it, settled, which is what espn.com now
   gets on the CLI (two of two runs: 93.7 % of the frame painted and an
   honest `animating`), and a page that does not comes back
   `settled: false, unsettledReason: "blank"` with a warning that names the
   colour and both things it can mean. The MCP schemas admit the reason on
   every surface, the README and the skill say what it is, and the fixture that reproduces it (an opaque veil at once, the
   content after `?delay=` ms) is the regression test for the CLI and for
   the live pane and window captures.

2. **Millimetres and device pixels are of the page as drawn.** A new
   `layoutScale` — the screen's width over the text scale, divided by the
   width the page laid out at, 1 whenever they agree — multiplies every
   length before it becomes millimetres (audit, inspect) or device pixels
   (every lint rule), while rects, font sizes and `pageHeight` stay in the
   page's own px, which is what a highlight in page space and the scroller
   work in. The walk-coverage note compares heights in the screen's px, so
   the one-screen page laid out 980 wide is one screenful. The scale is in
   every answer, a warning names the widths and the factor when it is not 1,
   and the lint's edge threshold is widened by it before the page is asked,
   since one device pixel is more of that page's px. berkshirehathaway.com
   at `android-65`: smallest text 0.69 mm (was 1.88), thirty of thirty-two
   text elements under the threshold (was seven), no image "upscaled 2×",
   no coverage warning. The same page with a viewport meta tag, as a
   fixture twin, is byte-for-byte what it was.

## Fixed on `feat/audit-groups-only`

3. **`obsrv_audit` takes `groupsOnly`** (`--groups-only` on the CLI), as the
   lint has since 0.32.0: the summary and the groups, an empty `findings`
   list, and no sentence about the list's cap — which the audit now says,
   as the lint does, when it prints a list that was cut. Headless the flag
   goes to the CLI; live the MCP leaves the list out of the app's answer.
   The summary and the groups count everything either way.

Not touched: a point given to `inspect` (`at`) or a rect given to
`highlight` on such a page is still read in the page's own px, which are
2.72× the screen's there; the same root cause, a fourth symptom, left for a
run that meets it.
