# The 0.54.0 candidate driven against a fresh set of live sites

The eleventh run, on `main @ 63f3fcb` — 0.53.0 plus the srcset fix, the
report-refusal fix and the load-error state — through the dev lane, against
bbc.com (news, srcset everywhere), stripe.com (a marketing page of drawn
UI), github.com (a product front page), developer.mozilla.org (long-form
documentation on a phone), airbnb.com (a retail home page behind a modal)
and vercel.com (a dark marketing page on a phone). Released 0.53.0 was
driven at the same URLs wherever a before-and-after mattered. The site is
the fixture; this reports on the tool.

## Held

- **No report was refused anywhere.** The failure that opened run 10 — a
  whole page's lint discarded, reported as a page that never answered —
  did not recur on any site, at any preset, headless or live. reuters.com
  itself now answers: 30 oversized images in three srcset groups, where
  0.53.0 exited 1.
- **Descriptors read correctly, including the ones that are not widths.**
  stripe.com credits "the 1x candidate"; vercel.com at android-65 credits
  "the 1284w candidate" and corrects for the phone's density (1284×1026
  drawn at 624×499 device px). bbc.com, whose `/news/` srcsets are written
  with no space after any comma, reports the same candidates as the
  released build does.
- **Long pages are walked and said to be walked.** developer.mozilla.org
  at android-65: 59 screenfuls of a 47,664 px page, `atEnd` true, and no
  findings — a page that earns its silence. bbc 13 screenfuls, stripe 14.
- **The rules still find things worth finding.** stripe.com: 233 thin-text
  findings (300 weight down to 8px), 37 contrast findings including a hero
  headline at 2.39:1 as stated. github.com: seven oversized images, four of
  them 2272×1520 files drawn at 558×375 with no srcset at all.

## Broke or misled, ranked

1. **A page locked behind a dialog: the walk scrolls the dialog and vouches
   for the page.** A consent wall, a paywall or an onboarding modal fixes the
   body in place, which collapses the document's scroll height and leaves the
   dialog's own panel as the only scroller in the light DOM. The walk finds
   that panel and scrolls it — and reports `walked: { screenfuls: 5, atEnd:
   true }`, which reads as a page walked to its end when the page never moved
   at all. Anything the page loads as it scrolls is never brought in, and is
   measured as absent.

   Pinned on a fixture rather than a site: `tests/fixtures/dialog-locked.html`
   is a locked page whose dialog scrolls, and it reproduces every time. The
   0.53.0 note written for the neighbouring case does not fire, because it is
   gated on the scroller being the root and here a scroller was found.

   Not a regression: released 0.53.0 behaves the same.

## A correction to what this run first reported

The finding above began as a claim about airbnb.com that does not survive
checking, and the record should say so rather than quietly improve.

What was first written: that airbnb's home page carries 267 interactive
elements and 41 images while the audit answered 11 targets and 1 text
element, so the measurement was dropping almost the whole page.

What is actually true. The 267 was a count of every interactive element in
the DOM, not of what any measurement would keep: applying the audit's own
`shown` filter to the same page leaves 84, because 162 of them have a zero
box. The 11-target answer and the snap that showed a full page behind a
dialog came from two *different* headless loads, so they were never
measuring the same page state. And a live audit of that site — one page
instance, measured in the running app — answers 121 targets, 280 text
elements, a 2,661 px page and real findings, including a 9.9 px search input
at 2.74 mm. Airbnb is not systematically under-measured.

What survived the checking is the mechanism, not the site: a locked page
whose dialog scrolls, which is reproducible on a fixture and is what the
first finding above now records. The lesson is the one from bbc.com earlier
in this same run — a count taken in a browser tab is not a measurement of
Obsrv's page, and two loads of a live site are not one experiment.

Observed and left alone: bbc.com mislabels its own srcset — one component
lists the same `ic/1920x1080/` file under 160w, 240w, 320w, 480w and 640w,
eight such candidates on the page — which is why a "160w candidate" is
reported as a 2560×1440 or 1024×576 file. The markup was read directly to
confirm it, and the released build reports it the same way; this is the
page being wrong and the rule being right, as nasa.gov's mislabelled 295w
candidate was in run 9.

Corrected in passing: bbc.com's no-space commas were at first taken for a
second site rescued by the srcset fix. They are not. Its URLs are about 100
characters, so a glued descriptor stays inside the 200-character bound that
reuters.com's 250-character resizer URLs broke. Both builds were run at the
same URL to settle it, and they agree to the finding.

## Fixed on `fix/walk-scrolled-a-dialog`

**The walk says when it scrolled a dialog rather than the page.** The page
scripts learn one fact — whether the container the walk moved sits inside a
`<dialog>`, `[role="dialog"]`, `[role="alertdialog"]` or `[aria-modal="true"]`
— and both walks, headless and live, add a sentence when that container was
scrolled while the document's own overflow was hidden: "the walk scrolled a
dialog, not the page: … the 5 screenfuls above are that dialog's and the page
never moved — content the page loads as it scrolls, and anything below the
first screen, was not brought into view before measuring".

Named dialog semantics only, deliberately. A page locked by an anonymous div
says nothing rather than the wrong thing, and the three conditions together —
an element scroller, inside a dialog, on a document that hides its overflow —
keep every neighbouring case quiet: an app shell whose inner container is the
content (spotify.com's player) fails the dialog test, and a dialog over a page
that can still scroll fails the third.

Why this is not the coverage note again, measured on both. The
walk-coverage note compares what the walk covered against the page it
measured, and catches a locked page whenever the dialog is short:
theguardian.com's consent wall gives "the walk saw the end after 4
screenfuls (5400 CSS px), but the page measures 21331 CSS px". A dialog
that scrolls *far*, though, inflates the apparent coverage until the
arithmetic looks satisfied — the fixture here walks 5 screenfuls of a 300 px
panel against a 2,264 px page, so `(5 + 1) x 1080` clears the page height and
the coverage note is silent. That is the gap: the more the dialog scrolls,
the less the old note can see, and the new one names the cause outright.

Nothing new appears in the tools' output shape. Every obsrv `outputSchema` is
`additionalProperties: false` and the SDK validates a result against the
schema the session listed at connect, so a new key would break sessions
already running; the sentence rides in `warnings`, where the reader is already
looking.
