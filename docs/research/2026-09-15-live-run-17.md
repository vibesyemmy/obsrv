# Run 17: a cold reader on fresh sites

Run 2026-09-15 by Rook for B1, on `main` at ebfb041, built first. Six sites and
a dev server, none of them used by runs 13–16. Chosen for shapes rather than
fame: an accessibility-audited government site as a control, a dense text site,
a design-led marketing site, a web-components site, an app-shell fixture over
localhost, a dark-theme link list, and a map.

**B1 is not met. Five findings, and one of them is the headline number.**

The reader was deliberately cold: I had never read `audit`, `lint` or `inspect`
output before this run.

---

## F5 — the contrast figure disagrees with the colours printed beside it

**The most serious, because contrast is what this product is for.**

`https://lobste.rs/`, `laptop-768-11`, headless. Both `lint` and `inspect`
agree with each other and neither agrees with arithmetic:

```
a.upvoter   color #ffffff   background #0c0c0c   contrast.asIs 7.5
```

White on `#0c0c0c` is **19.6:1** by the WCAG 2 formula. Not 7.5:1.

The formula is not generally wrong — on `https://www.gov.uk/browse/benefits`
the same tool reports `#0b0c0c on #d2e2f1 → 14.82:1`, and the formula gives
14.81:1. It is right there and wrong here.

A ratio of 7.5 for white text implies a background luminance near 0.09, which
is about `#545454` — a mid grey, not `#0c0c0c`. So the likely mechanism is that
the ratio is computed against a *composited* background while the sentence
prints the element's *computed* `background-color`, or the reverse. Which half
is right is for whoever takes this; that the two halves contradict each other is
not in doubt, and a reader cannot tell which number to act on.

It also changes verdicts, not just figures: 242 `contrast-on-panel` findings on
that page rest on it, including 217 of plain white-on-black reported as
"passes on the display it was designed on, fails on this one".

## F1 — every text link is exempt from the tap-target measure, not only those in running text

`https://www.gov.uk/browse/benefits`, `android-65`: `targets.count: 8` on a
4,678 px page built from link lists. `https://lwn.net/`, `iphone-61`: 214 text
elements measured, **`targets.count: 1`**, on a page that is almost entirely
article links.

Settled on a fixture rather than inferred from a live DOM — viewport meta,
`layoutScale: 1`, no warnings. Seven interactive elements: one inline link in a
sentence, two list links, two nav links, one button, one inline-block styled
link. `targets.count: 2` — the button and the styled link. The four links that
are **not** in running text are 19 px tall, 3.58 mm, half the 7 mm threshold,
and are not reported at all.

The rule, `src/shared/audit.ts:183`:

```ts
const inlineLink = el.tagName === 'A' && cs.display === 'inline'
if (inlineLink && !iconOnly) continue
```

The code comment is honest — exempt "when the link *is* text". **The tool's
description says "Inline links in running text are exempt from the target rule,
as in WCAG 2.5.8"**, which is the narrower rule and not what runs. On a page
navigated by text links, `obsrv_audit` reports a small count and few findings,
and a reader concludes the tap targets are fine.

Whether a list of links *should* be exempt is arguable: WCAG 2.5.8's exception
covers a target in a sentence, or one whose size is constrained by the
line-height of surrounding non-target text. That the description and the
behaviour differ is not arguable.

## F4 — the app-shell warning contradicts the finding printed beside it

`http://127.0.0.1:8899/app-shell-findings.html` (the repo's own fixture, served
over localhost), `laptop-768`, lint:

> the walk scrolled a panel on the page, not the page itself … the page never
> moved — content the page loads as it scrolls, **and anything below the first
> screen, was not brought into view before measuring**

In the same reply: a finding on `p#deep-text` at **y = 1552**, below a 768 px
screen. The fixture puts that element inside `#scroller`, which is the panel the
walk scrolled — so it *was* brought into view, and that is exactly how a lazy
image there would have loaded.

The warning cannot tell "the walk scrolled the app's content scroller, which is
the right thing to scroll" from "the walk scrolled a side panel and missed the
page". It asserts the pessimistic reading in both cases. On an app shell — a
mail client, a dashboard, anything with a fixed chrome — the tool reports that
it did not see below the fold immediately after having seen below the fold.

Worth noting where this sentence came from: it was written for the *capture*
path, where a headless full-page capture genuinely cannot reach an app shell.
It is true there and false here. One sentence serving two surfaces.

## F3 — one element, two colours, one run

`https://stripe.com/gb`, `laptop-768`, `budget-tn`, a single lint call:

```
contrast          #81b81a on #ffffff is 2.39:1   span.hero-section__title-copy  x171 y267.6 884.2×165
contrast-on-panel #000eff on #ffffff is 3.09:1   span.hero-section__title-copy  x171 y267.6 884.2×165
```

Same class, same rect to the pixel, and
`span.hero-section__title-copy ~ span.hero-section__title-copy` returns
`found: false` — there is no stacked sibling. One element, read twice at
different moments, because Stripe animates the hero colour.

The two sentences disagree about the verdict and not merely the figure: one
fails as stated, the other passes as stated and fails on the panel. Nothing says
the colour is in motion.

**This is B2's limitation from a new side.** The motion probe measures the page
twice, 250 ms apart, and keys off the elements' own boxes. A colour that
animates while the geometry holds still is a page the probe calls settled.

## F2 — `obsrv_inspect` answers confidently about an element with no box

`https://www.gov.uk/browse/benefits`: a selector matched a hidden anchor and
returned `found: true`, `rect` 0×0, `rectMm` 0×0 — and a full readout: font
19 px, colour `#1a65a6`, contrast 5.69, `passesAsIs: true`, `notes: []`.

A visible element returns a real box, so the zero is the element's own rather
than a failure to measure. `obsrv_audit` explicitly skips hidden and zero-size
elements; `inspect` does not say when it has hit one, so an agent asking what is
at a selector gets contrast figures for something nobody can see.

## What held, and is worth not losing

Four sentences did their job well enough to name:

- **openstreetmap.org answered 503**, and the warning said so: *"the figures are
  of the error page it sent, not of the page asked for."* Without it,
  `0 targets, 2 texts` reads as a clean page.
- **caniuse.com**: *"57 shadow roots hold 188 of this page's 238 text elements,
  which the measurement does not enter: the figures are of the light DOM
  alone."* Seventy-nine per cent of the page unmeasured, declared.
- **stripe.com**: *"3 text elements sit on an image or gradient and got no
  contrast verdict: the pixels under it are not a colour anyone stated"*, with
  `skipped.textOnImages: 3` agreeing with it.
- **A fixture with no viewport meta**: *"the page lays out 980 CSS px wide where
  the screen gives it 360 and is drawn at 0.37× to fit."* It stopped me
  misreading my own fixture's millimetres, which is the warning earning its
  keep on its first outing.

Three of those five findings are the same defect class the criterion names: a
sentence that is plausible alone and wrong beside its neighbour. F5 contradicts
arithmetic, F4 contradicts the finding under it, F3 contradicts itself. None
would be visible to anyone scanning for errors — each half looks correct.
