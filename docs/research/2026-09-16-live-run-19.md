# Run 19 — the live app

Rook, 2026-09-16, on Opeyemi's word in Rook's session. Card: `b1-live-app`.

B1's last documented gap. Runs 17 and 18 were headless throughout and each wrote
that exclusion into its own result. This is the first time anyone on this board
has read what an agent driving the visible app is told.

## Pre-registered before the first call

Written before any tool was invoked, so that a clean result cannot be produced
by choosing the checks afterwards.

### What the run is for

Not *does the live path work*. The question is: **would an agent driving the
app, reading only what it is told, form a correct picture of what the window is
showing — and would it notice when it had not?** A call that succeeds and says
something slightly wrong is the finding. A call that fails loudly is not.

### The vacuity check — what would mean this run exercised nothing

The card names three. All three are adopted, plus one of Rook's:

1. **Every call answering `navigated: false`** on a window nobody was watching.
2. **A session where the app was never actually frontmost** — the drive
   surface can report success against a window that is not the one on screen.
3. **Every finding read is one the headless path already produced.** The
   subtle one: the live surface exercised but not *read*.
4. **Rook's, and the one to apply per call:** if I cannot name, for a given
   call, a fact in its reply that **only a live window could have produced**,
   that call exercised nothing live. A reply that would read identically from
   a headless render is not evidence about the live path.

If the run ends and any of these holds, the result is *this run did not
exercise the live app*, and it is reported in those words rather than as a
quiet pass.

### The order, chosen because mistakes move Opeyemi's window

Cheapest and most reversible first. Nothing that navigates or resizes until the
read-only calls have behaved.

1. `status` — reads, moves nothing.
2. `presets` — reads, moves nothing.
3. A fixture page, local, before any real site.
4. Scroll, highlight — visible, reversible.
5. `capture: 'pane'`, onion skin.
6. `audit` / `lint` / `inspect` in live mode.
7. Real sites only once all of the above behave.

### The instrument, and it is not a test

Opeyemi is at the desk. After each call I state in one line what the reply
claims, and ask whether that matches what he can see. **A person watching the
same window is a better check on "what an agent is told" than any assertion I
could write, and it is available only while he is there.** Disagreements
between the reply and the screen are the findings.

### Known hazards, from the card, so a limit is not filed as a defect

- A second instance clobbers `control.json`; the drive and the reader can end
  up on different windows. Check `tabId` rather than assume.
- The tools act on the FRONT tab, resolved per command. The user can move it.
- `focusWindow` / `app.focus({steal})` is refused on macOS 14+ unless the
  front app yields. That is the OS.
- `report` stays headless by design. Not a gap in this run.

### What this run does not close

Run 17's two remaining sites, and whether the report overview's pins and crops
land where the findings are. B1 is met when a run finds nothing user-visible;
runs 13–18 each found something.

## Five findings, and two of them are not about the live path

Applying the pre-registered vacuity check honestly, before listing them:
**three of the five rest on facts only a live window could produce; two do
not.** Criterion 3 said a run where every finding is one the headless path
already produces has exercised the surface without reading it. That has not
happened — but two findings below were *found* live and are not *about* live,
and saying so is the difference between five live findings and three.

| # | finding | live-only? |
| --- | --- | --- |
| 1 | the status reply contradicts its own field description at launch | **yes** |
| 2 | `inspect` says nothing when a point is off the screen | no — headless does this too |
| 3 | a read-only `drive` call launches the app | **yes** |
| 4 | `onionSkin` returns `0` for three different facts | **yes** |
| 5 | `groupsOnly` empties `findings` silently | no — headless does this too |

### 1. At launch, `presetId` and `cssWidth` describe two different moments

The first call of the run — `obsrv_drive` with no arguments, which also
launched the app — returned `presetId: "pixel-8"` and `orientation: "portrait"`
beside `cssWidth: 1920`, `cssHeight: 1080`, `screenShape: "landscape"`, and
`loading: false`.

`pixel-8` is 412×915 (`obsrv_presets`). Both halves are internally consistent —
`orientation` follows the preset, `screenShape` follows the dimensions — which
is what makes the reply read as settled rather than as a page catching up.

**It is a defect by the tool's own contract**, which is the framing Henry
supplied and the one the card should lead with: `driveOutputShape` promises
`cssWidth` is *"the CSS viewport the target is rendering at, already rotated"*.
At launch it is not. Mechanism, also Henry's: `presetId` comes from the
restored store while `cssWidth` comes from the offscreen surface
(`src/main/ipc.ts:1493-1499`), and at launch those are two different moments.

**My first account of this was wrong and the correction is the point.** I wrote
that `drive` was reporting the window under unqualified names. The next two
calls refuted it — `laptop-768` → 1366×768, `pixel-8` → 412×915, both correct.
Had I filed at the first reply I would have shipped a card whose mechanism was
wrong, on a run about whether a reply lets a reader form a correct picture.
**The one-reply version was coherent, specific and wrong**, which is what an
agent reading that status does.

**One observation, unreproduced.** Reproducing it means quitting Obsrv and
relaunching, which closes the window Opeyemi is working in. For whoever takes
it: quit the app, leave a phone preset on the active tab, call `obsrv_drive`
with no arguments, read the first status.

### 2. A point that is not on the screen is answered as an empty point

`obsrv_inspect` at `(1000, 500)` on a 412-wide screen: `found: false`,
`readout: null`, `notes: []`. No note that the coordinate is off the screen.
So `found: false` carries *nothing is there* and *that point does not exist
here* — opposite facts, one output.

**What makes it a defect rather than a preference is that the same app already
does it right, in the same tool family.** `obsrv_drive`'s `highlight`, given a
page rect that is scrolled out of view, answers `drawn: false` **and**
`"the page rect is off screen at the current scroll (0, 1536); scroll it into
view first"` — the reason, the state that caused it, and the fix. Two calls
apart, the same class of caller mistake, opposite treatment.

### 3. The one call that reads nothing starts the application

`obsrv_drive` with no arguments is documented as *"none = just read the current
state"*. It returned `launched: true`: it started Obsrv on the user's desk.
`obsrv_snap`, `obsrv_audit`, `obsrv_lint` and `obsrv_inspect` all say in their
own descriptions that they launch the app if it is not running. **`obsrv_drive`
does not — and it is the call an agent reaches for first precisely because it
reads as safe.**

Two halves, and they belong to different people: *whether* an empty drive call
should launch at all is a product decision; that its description says it only
reads while `launched: true` exists is a sentence to fix.

### 4. `onionSkin: 0` means three different things and says which for none

`obsrv_drive` with `onionSkin: 0.5` at `ultrawide-34` returns `onionSkin: 0`,
`warnings` absent, no note. The documented behaviour is correct — the app
cannot render a 2x reference for that viewport at 1x — but the reply does not
carry it.

**Control:** the same command at `laptop-768` returns `onionSkin: 0.5`. So the
readback works and the `0` is a real refusal rather than a dead field.

The field's own description names *two* meanings of `0` — off, and an app older
than the field. **The third, the one an agent actually hits, is not among
them.** And `driveOutputShape` already carries `warnings: z.array(z.string())`,
so a sentence costs no schema change and breaks nothing.

### 5. `groupsOnly: true` empties `findings`, and only the summary disagrees

A live audit with `groupsOnly: true` returned `findings: []` and
`truncated: {findings: 0}`. **Those are the two fields that answer "were there
findings", and both said no.** `summary.targets.under: 2` and a populated
`groups` disagreed, in the same object.

Nothing echoed the flag and no note mentioned it. **Control:** the same audit
without `groupsOnly` returns two findings, so the empty list was the flag and
not the page. Minor — a careful reader has `summary` — and real.

## What behaved well, recorded because a run that only lists defects is not a reading

- **`highlight` is the standard the rest should meet**: `drawn` true or false,
  the resolved pane rect so the caller can check the mapping itself
  (page y 2000 at scroll 1536 → pane y 464), and on failure a sentence naming
  the reason, the current scroll, and what to do about it.
- **`scroll` says what it actually did**: `scrolled: {x, y}`, `scroller`,
  `atEnd` — the tool's own description tells you to compare `scrolled` against
  what you asked for rather than trusting success, and the field is there to
  do it with.
- **A clean lint is legible as clean**: every rule listed at zero, `skipped`
  and `truncated` broken out, on a fixture that does have audit findings — so
  the zeros are a measurement rather than an absence.
- **`walked: {screenfuls: 11, atEnd: true, ms: 3922}`** — the walk reports its
  own extent, which is what makes a measurement of a long page believable.
